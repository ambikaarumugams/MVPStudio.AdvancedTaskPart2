## 🔹 Compile Time

* The phase when your **C# code is converted into IL (Intermediate Language)** by the compiler.
* Errors found here are called **compile-time errors**.
* They prevent the program from even starting.

### Examples of **compile-time errors**

```csharp
int x = "Hello";   // ❌ Type mismatch
Console.Writeline("Hi"); // ❌ Spelling mistake in method name
int y; 
Console.WriteLine(y); // ❌ Use of uninitialized variable
```

👉 If the compiler cannot understand your code or resolve types → compile-time error.

---

## 🔹 Runtime

* The phase when the program is actually **executed by the CLR (Common Language Runtime)**.
* Errors found here are called **runtime errors**.
* They happen **while the program is running**, even if it compiled successfully.

### Examples of **runtime errors**

```csharp
int a = 10, b = 0;
Console.WriteLine(a / b); // ❌ DivideByZeroException at runtime

int[] arr = {1,2,3};
Console.WriteLine(arr[5]); // ❌ IndexOutOfRangeException at runtime

string s = null;
Console.WriteLine(s.Length); // ❌ NullReferenceException
```

👉 Code compiles fine, but **fails during execution**.

---

## 🔹 Key Differences

| Feature          | Compile Time                                   | Runtime                                                        |
| ---------------- | ---------------------------------------------- | -------------------------------------------------------------- |
| **When**         | Before execution (build time)                  | During execution                                               |
| **Checked by**   | Compiler                                       | CLR (runtime environment)                                      |
| **Errors**       | Syntax errors, type errors, missing references | Exceptions like divide by zero, null reference, file not found |
| **Fix**          | Must be fixed before running                   | Can be handled with `try–catch`                                |
| **Polymorphism** | **Overloading** is resolved at compile time    | **Overriding** is resolved at runtime                          |

---

## 🔹 Analogy

* **Compile time** = teacher checking your exam paper before submitting (grammar/spelling mistakes).
* **Runtime** = you actually giving a speech in class → if you forget lines or mic stops working, errors happen at runtime.

---

✅ **In short**:

* **Compile time** = code translation & static checks.
* **Runtime** = actual execution in memory by CLR.

### 🔹 Step 1: Write Code

* You write C# code in `.cs` files.
* Example:

```csharp
int x = 10, y = 0;
Console.WriteLine(x / y);
```

---

### 🔹 Step 2: Compile Time

* Compiler checks for:

  * Syntax errors (missing `;`, misspelled keywords).
  * Type checking (`int` vs `string` mismatch).
  * Variable declarations.
* If errors → program won’t build.

✅ If successful → generates **IL code** (`.dll` or `.exe`).

---

### 🔹 Step 3: Runtime

* The **CLR (Common Language Runtime)** takes the IL code and executes it.
* Now, unexpected issues can occur:

  * Divide by zero
  * File not found
  * Null reference
  * Out of memory

👉 These are **runtime errors (exceptions)**.

---

### 🔹 Step 4: Exception Handling

* If runtime errors occur, program **throws exceptions**.
* Without handling → program **crashes**.
* With handling (`try–catch–finally`) → program **recovers gracefully**.

Example:

```csharp
try
{
    int x = 10, y = 0;
    Console.WriteLine(x / y); // runtime error
}
catch (DivideByZeroException ex)
{
    Console.WriteLine("Cannot divide by zero!");
}
finally
{
    Console.WriteLine("Execution finished.");
}
```

## 🔹 What is Exception Handling?

* An **exception** is an unexpected event/error that occurs at runtime (like dividing by zero, file not found, null reference, etc.).
* **Exception handling** is the mechanism to **detect, handle, and recover** from these errors without crashing the program.

---

## 🔹 Why we use Exception Handling in C#

### 1. **Prevent program crash**

Without handling:

```csharp
int x = 10, y = 0;
int result = x / y;   // ❌ System.DivideByZeroException → program crashes
```

With handling:

```csharp
try
{
    int result = x / y;
}
catch (DivideByZeroException ex)
{
    Console.WriteLine("Cannot divide by zero!");
}
```

👉 Program continues safely.

---

### 2. **Provide meaningful error messages**

Instead of ugly system errors, you can show **user-friendly messages**:

```csharp
catch (FileNotFoundException)
{
    Console.WriteLine("File not found. Please check the path.");
}
```

---

### 3. **Graceful recovery**

Exceptions let you **recover and continue** instead of exiting:

```csharp
try
{
    string text = File.ReadAllText("data.txt");
}
catch (FileNotFoundException)
{
    File.WriteAllText("data.txt", "Default content"); // recover by creating file
}
```

---

### 4. **Separate error-handling logic from normal code**

Keeps your **main logic clean** and error handling in one place:

```csharp
try
{
    ProcessData();
}
catch (Exception ex)
{
    LogError(ex);
}
```

---

### 5. **Maintain application stability**

* In large apps, unhandled exceptions could crash servers.
* Exception handling ensures **stability and reliability**.

---

## 🔹 Analogy

Imagine driving a car 🚗:

* Exceptions = potholes on the road.
* Exception handling = shock absorbers + brakes → they don’t remove potholes, but help you **handle them safely** and continue driving.

---

✅ **In summary**:
We use exception handling to:

1. Prevent program crashes
2. Show meaningful messages
3. Recover gracefully
4. Keep code clean
5. Ensure stable, reliable software

Do you want me to also explain the **different keywords (`try`, `catch`, `finally`, `throw`) with examples**?

Perfect 👍 Let’s go through all the **exception handling keywords in C#** with examples.

---

## 🔹 1. `try`

* Block of code where you put statements that may throw an exception.
* Only **one `try` per group**, but multiple `catch` blocks can follow.

```csharp
try
{
    int x = 10, y = 0;
    int result = x / y;   // ❌ DivideByZeroException
}
```

---

## 🔹 2. `catch`

* Handles the exception thrown inside `try`.
* Can have **multiple `catch` blocks** for different exception types.
* More specific exceptions should come **before** general ones.

```csharp
try
{
    string text = File.ReadAllText("data.txt");
}
catch (FileNotFoundException ex)
{
    Console.WriteLine("File not found.");
}
catch (Exception ex)
{
    Console.WriteLine("General error: " + ex.Message);
}
```

---

## 🔹 3. `finally`

* Always executes, whether an exception occurs or not.
* Commonly used to **release resources** (close file, database connection, driver, etc.).

```csharp
FileStream fs = null;

try
{
    fs = new FileStream("data.txt", FileMode.Open);
    // read file
}
catch (IOException ex)
{
    Console.WriteLine("Error reading file.");
}
finally
{
    if (fs != null)
        fs.Close();   // ✅ always executed
    Console.WriteLine("File closed.");
}
```

---

## 🔹 4. `throw`

* Used to **explicitly raise an exception**.
* Can throw a new one, or re-throw the current one.

```csharp
// Throwing a new exception
if (age < 18)
    throw new InvalidOperationException("Age must be at least 18.");

// Re-throwing inside a catch
try
{
    int x = 0;
    int y = 10 / x;
}
catch (DivideByZeroException)
{
    Console.WriteLine("Logging error...");
    throw;   // re-throws to outer layer
}
```

---

## 🔹 5. Example Putting It All Together

```csharp
try
{
    int[] arr = { 1, 2, 3 };
    Console.WriteLine(arr[5]);   // ❌ IndexOutOfRangeException
}
catch (IndexOutOfRangeException ex)
{
    Console.WriteLine("Index is out of range!");
}
catch (Exception ex)
{
    Console.WriteLine("Some other error: " + ex.Message);
}
finally
{
    Console.WriteLine("Cleanup done.");
}
```

**Output**

```
Index is out of range!
Cleanup done.
```

---

## ✅ Summary

* `try` → risky code
* `catch` → handles exceptions
* `finally` → always executes (cleanup)
* `throw` → raise/re-raise exceptions

## 🔹 When to Use `try–catch`

Use it around code that may **fail at runtime** due to external or unpredictable conditions.

### 1. **I/O operations**

* Reading/writing files
* Accessing databases
* Calling web services or APIs

```csharp
try
{
    string content = File.ReadAllText("data.txt");
}
catch (IOException ex)
{
    Console.WriteLine("Problem reading the file: " + ex.Message);
}
```

---

### 2. **User input validation**

If user enters invalid data that could cause exceptions.

```csharp
try
{
    int age = Convert.ToInt32(Console.ReadLine());
}
catch (FormatException)
{
    Console.WriteLine("Please enter a valid number!");
}
```

---

### 3. **Network operations**

When calling external APIs, servers, or cloud services → failures are common.

```csharp
try
{
    var response = await httpClient.GetStringAsync("https://api.example.com");
}
catch (HttpRequestException ex)
{
    Console.WriteLine("Network error: " + ex.Message);
}
```

---

### 4. **Resource management**

When dealing with files, streams, sockets, drivers, etc.
Combine with `finally` to ensure proper cleanup.

```csharp
SqlConnection conn = null;
try
{
    conn = new SqlConnection("...");
    conn.Open();
}
catch (SqlException ex)
{
    Console.WriteLine("Database error: " + ex.Message);
}
finally
{
    conn?.Close();
}
```

---

### 5. **Critical sections**

Where you **cannot let the application crash**, e.g.:

* Payment processing
* Authentication logic
* Logging operations

---

## 🔹 When NOT to Use `try–catch`

❌ Don’t wrap **every line of code**.

* Simple assignments (`int x = 5;`) don’t need it.
* Overusing `try–catch` makes code messy and slower.

Instead:

* Use **input validation** before risky operations.
* Reserve `try–catch` for things **beyond your control** (file missing, network down, database offline, etc.).

---

## 🔹 Best Practices

1. **Catch the most specific exception first**, then general (`Exception`) last.
2. **Log the exception** instead of silently ignoring it.
3. Use `finally` (or `using`) to release resources.
4. Don’t use `try–catch` to control normal program flow (bad practice).

---

✅ **In short**:
Use `try–catch` only where something can genuinely fail at runtime due to **external or unpredictable conditions**.
Not for simple logic errors you can check before executing.
